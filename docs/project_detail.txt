SISTEMA DE GESTIÓN DE RESERVAS DE ALOJAMIENTO EN HOTELES

Desarrollaremos una **aplicación móvil nativa Android para la gestión de reservas de alojamiento en hoteles**, correspondiente al proyecto del curso **1TEL05 – Servicios y Aplicaciones para IoT**.

El sistema debe seguir estrictamente los requerimientos funcionales, técnicos, arquitectónicos y de diseño indicados a continuación.

La aplicación debe estar orientada principalmente a la gestión de reservas de hoteles, pero también debe integrar un sistema de taxis para transporte al aeropuerto.

---

# 1. OBJETIVO GENERAL

Desarrollar un sistema que permita gestionar reservas de alojamiento en hoteles mediante una aplicación móvil, permitiendo la interacción entre:

* Clientes.
* Administradores de hoteles.
* Conductores de taxi.
* Superadmin.

El sistema estará compuesto por:

1. **Aplicación móvil Android principal**, utilizada por clientes, administradores de hoteles, conductores de taxi y Superadmin según sus respectivos roles.
2. **Aplicación web independiente para conductores de taxi**, utilizada para su registro y administración.
3. **REST API** que permita la comunicación entre la aplicación móvil y el sistema web de taxis.

La aplicación debe permitir gestionar:

* Usuarios.
* Hoteles.
* Habitaciones.
* Servicios.
* Reservas.
* Pagos simulados.
* Calificaciones.
* Comentarios.
* Chat cliente-hotel.
* Servicios de taxi.
* Cargos adicionales.
* Notificaciones.
* Reportes.
* Logs.

---

# 2. REFERENCIA DE DISEÑO: BOOKING

La aplicación móvil debe tomar como **principal referencia visual y de experiencia de usuario la aplicación móvil de Booking.com**, ya que esta fue utilizada como referencia para el diseño del proyecto.

La referencia debe utilizarse principalmente para:

* Organización de la información.
* Flujo de búsqueda.
* Presentación de hoteles.
* Cards.
* Fotografías.
* Filtros.
* Selección de fechas.
* Presentación de precios.
* Flujo de reserva.
* Gestión de reservas.
* Navegación.
* Claridad de las acciones.

## IMPORTANTE

La aplicación **NO debe ser una copia de Booking**.

No utilizar:

* Logotipo de Booking.
* Nombre de Booking como parte de la aplicación.
* Textos propietarios.
* Imágenes propietarias.
* Identidad visual idéntica.
* Colores o elementos de marca de manera que parezca una aplicación oficial de Booking.

Se debe desarrollar una **identidad visual propia**, pero utilizando principios de UX/UI similares a una aplicación moderna de reservas como Booking.

La prioridad es conseguir una experiencia:

**simple + visual + rápida + intuitiva + orientada a reservas.**

La aplicación móvil debe desarrollarse como:

* Android nativo.

* Kotlin.

* Flutter.
* React Native.

* LiveData.
* Navigation Component.
* Material Components.

siempre que aporten a una arquitectura limpia y mantenible.

* Administrar información del hotel.

* Administrar habitaciones.

* Consultar clientes.
* Gestionar cargos adicionales.

Puede:

* Registrarse mediante la aplicación web.

* Consultar solicitudes disponibles.

* Escanear el QR del cliente.
* Finalizar el servicio.
* Recibir calificaciones.

## 6.4 Superadmin

El Superadmin administra el sistema.

Puede:

* Gestionar usuarios.

* Rechazar conductores.
* Gestionar hoteles.
* Gestionar administradores de hoteles.
* Consultar reportes de ventas.
* Consultar logs.

El Superadmin **NO funciona como cliente ni como administrador de hotel**.

`[Wi-Fi] [Piscina] [Gimnasio] [Desayuno] [Estacionamiento]`

`[✓ Wi-Fi] [✓ Piscina] [ ] Gimnasio`

`[✓ Desayuno] [ ] Spa] [✓ Estacionamiento]`

Los tags seleccionados deben tener un estado visual diferente.

Se recomienda utilizar:

* Material Chips.
* FilterChips.
* Chips seleccionables.
* RecyclerView cuando existan muchos servicios.

El proceso debe ser rápido y visual.

# 15. SERVICIOS INCLUIDOS Y SERVICIOS ADICIONALES

Los servicios deben dividirse en:

## Servicios incluidos

Son servicios incluidos en la reserva.

Ejemplo:

* Wi-Fi.
* Piscina.
* Desayuno.

No requieren un precio adicional.

## Servicios adicionales

Son servicios que tienen un costo adicional.

Ejemplo:

* Lavandería.
* Traslado al aeropuerto.
* Servicio a la habitación.

Estos deben permitir definir un precio.

---

# 16. FLUJO DE REGISTRO DE SERVICIOS

El flujo debe ser:

**Registrar hotel → Servicios → Seleccionar tags → Clasificar → Definir precio si corresponde → Guardar**

Ejemplo:

### Servicios incluidos

* Wi-Fi.
* Piscina.
* Desayuno.

### Servicios adicionales

* Lavandería — S/ 20.
* Traslado al aeropuerto — S/ 50.

El precio solamente debe solicitarse para servicios adicionales.

---

# 17. CATÁLOGO GLOBAL DE SERVICIOS

Cada servicio del sistema debe existir como un elemento del catálogo global.

Cada servicio debe tener como mínimo:

* `serviceId`
* `name`
* `description`
* `icon/image`
* `active`

El administrador del hotel selecciona servicios existentes.

No debe crear manualmente un nuevo servicio desde la configuración del hotel.

Esto permite:

* Evitar duplicados.
* Estandarizar nombres.
* Facilitar filtros.
* Reutilizar servicios.
* Mantener consistencia.

---

# 18. RELACIÓN HOTEL-SERVICIO

El precio y la clasificación del servicio deben pertenecer a la relación entre hotel y servicio.

Modelo conceptual:

### Servicio

* ID.
* Nombre.
* Descripción.
* Icono/imagen.
* Estado.

### HotelServicio

* `hotelId`
* `serviceId`
* `included`
* `price`

Ejemplo:

**Servicio global:**

Piscina.

**Hotel A:**

Piscina → Incluida.

**Hotel B:**

Piscina → Adicional → S/ 25.

El mismo tag puede ser utilizado por múltiples hoteles.

---

# 19. VISUALIZACIÓN DE SERVICIOS

En el detalle del hotel mostrar:

### Servicios incluidos

`Wi-Fi` `Piscina` `Gimnasio` `Desayuno`

### Servicios adicionales

`Lavandería — S/ 20`

`Traslado al aeropuerto — S/ 50`

Los servicios deben visualizarse mediante:

* Tags.
* Chips.
* Cards pequeñas.

Debe mantenerse una interfaz limpia.

---

# 20. FILTROS POR SERVICIOS

El catálogo de servicios también debe utilizarse durante la búsqueda.

Ejemplo:

**Filtros**

`[Wi-Fi] [Piscina] [Gimnasio] [Desayuno]`

Si el cliente selecciona:

**Piscina + Gimnasio + Wi-Fi**

mostrar hoteles que tengan dichos servicios asociados.

Por lo tanto, los mismos tags sirven para:

**Registrar hoteles → Mostrar servicios → Filtrar hoteles**

---

# 21. REGLAS DEL SISTEMA DE SERVICIOS

Cumplir obligatoriamente:

1. Los servicios pertenecen a un catálogo global.
2. Cada servicio tiene un ID único.
3. Los hoteles seleccionan servicios existentes.
4. No se deben duplicar servicios dentro de un mismo hotel.
5. Los servicios pueden ser incluidos o adicionales.
6. Los servicios adicionales deben tener precio.
7. Los servicios incluidos no necesitan precio adicional.
8. El precio pertenece a la relación hotel-servicio.
9. Un mismo servicio puede utilizarse en múltiples hoteles.
10. Los tags deben utilizarse también como filtros.
11. El administrador no debe escribir manualmente el nombre del servicio.
12. La selección debe ser visual mediante chips/tags.

# 56. REGLAS IMPORTANTES Y OBLIGATORIAS

Cumplir obligatoriamente:

1. Java, no Kotlin.
2. XML, no Jetpack Compose.
3. Android 14 / API 34 como mínimo.
4. Aplicación móvil nativa.
5. Persistencia NoSQL.
6. REST API para taxis.
7. Nunca conectar directamente la aplicación móvil con la BD de taxis.
8. RecyclerView para listas.
9. Rating de 1–10.
10. Administradores de hotel NO son clientes.
11. Superadmin administra el sistema y usuarios, además de reportes y funciones administrativas correspondientes.
12. No permitir reservas superpuestas.
13. Chat únicamente durante reservas activas.
14. Mínimo 4 fotografías por hotel.
15. Separar servicios incluidos y adicionales.
16. Los servicios deben utilizar tags predefinidos.
17. El administrador no debe escribir manualmente nombres de servicios.
18. Un servicio puede pertenecer a múltiples hoteles.
19. Un servicio puede ser incluido en un hotel y adicional en otro.
20. El precio del servicio adicional pertenece a la relación hotel-servicio.
21. Los tags deben utilizarse también como filtros de búsqueda.
22. El taxi debe seguir exactamente los estados definidos.
23. El QR debe utilizarse para finalizar el servicio.
24. La ubicación del conductor debe actualizarse periódicamente durante un servicio activo.
25. Una falla de la API de taxis no debe impedir las reservas de hoteles.
26. Las contraseñas nunca deben almacenarse en texto plano.
27. Las operaciones deben estar restringidas según el rol.
28. La aplicación debe tener una identidad visual propia.
29. Booking debe utilizarse únicamente como referencia de UX/UI.
30. No copiar la identidad visual de Booking.
31. La interfaz debe ser limpia, moderna, intuitiva y orientada a reservas.
32. Los componentes visuales deben ser reutilizables.
33. La lógica de negocio debe mantenerse separada de las Activities.
34. Los datos mock deben estar separados de la interfaz.
35. La arquitectura debe permitir reemplazar los mocks por las fuentes de datos reales.

# 57. RESULTADO FINAL ESPERADO

El resultado debe ser una aplicación móvil Android nativa, funcional, moderna y escalable para gestionar reservas de alojamiento y servicios de taxi.

Debe combinar:

**Requerimientos del proyecto + Java/XML + Android 14 + NoSQL + REST API + diseño inspirado en Booking + sistema de tags de servicios + gestión de hoteles + reservas + pagos + chat + taxis + reportes + seguridad.**

La aplicación debe sentirse como una aplicación moderna de reservas de alojamiento, pero debe conservar una **identidad visual propia**.

El sistema debe permitir que:

* Los clientes encuentren y reserven hoteles fácilmente.
* Los administradores gestionen sus hoteles de manera sencilla.
* Los servicios puedan configurarse rápidamente mediante tags predefinidos.
* Los servicios puedan utilizarse como filtros.
* Los conductores gestionen servicios de taxi.
* El Superadmin controle usuarios y operaciones administrativas.
* Toda la información esté organizada y separada según el rol.

La prioridad general del proyecto es:

**USABILIDAD + CLARIDAD + SEGURIDAD + ESCALABILIDAD + CONSISTENCIA VISUAL + CUMPLIMIENTO DE LOS REQUERIMIENTOS DEL PROYECTO.**

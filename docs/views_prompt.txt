# PROMPT MAESTRO — DISEÑO UI/UX DE LA APLICACIÓN MÓVIL DE RESERVAS DE HOTELES

## 0. PROPÓSITO DEL PROMPT

Diseña y desarrolla la **interfaz visual completa de una aplicación móvil Android nativa para reservas y gestión de alojamiento en hoteles**, perteneciente al proyecto del curso **1TEL05 – Servicios y Aplicaciones para IoT**.

Este prompt está dirigido principalmente al **diseño e implementación de las vistas de la aplicación móvil**.

La prioridad NO es diseñar la arquitectura backend, la base de datos, las APIs ni la lógica interna del sistema.

La prioridad absoluta debe ser:

> **crear una aplicación móvil visualmente excelente, moderna, elegante, consistente, intuitiva, reutilizable y suficientemente pulida como para destacar por su frontend.**

El resultado debe sentirse como un producto real y profesional, no como una colección de pantallas de un proyecto universitario.

---

# 1. CONTEXTO FUNCIONAL MÍNIMO

La aplicación pertenece a un sistema de reservas de hoteles.

El usuario principal es el **cliente**, quien debe poder:

* Buscar hoteles.
* Seleccionar destino.
* Seleccionar fechas.
* Seleccionar huéspedes.
* Filtrar resultados.
* Explorar hoteles.
* Consultar fotografías.
* Consultar habitaciones.
* Consultar servicios.
* Reservar.
* Consultar sus reservas.
* Gestionar reservas.
* Realizar un pago simulado.
* Comunicarse con el hotel durante una reserva activa.
* Realizar checkout.
* Calificar el hotel.
* Solicitar un taxi al aeropuerto.
* Consultar el taxi asignado.
* Visualizar información del conductor y vehículo.
* Seguir el estado del servicio.
* Calificar al conductor.

Existen además otros roles:

* Administrador de hotel.
* Conductor de taxi.
* Superadmin.

La aplicación móvil puede cambiar de interfaz según el rol autenticado.

**No es necesario implementar en este trabajo la lógica backend completa.**

Cuando sea necesario representar información todavía no conectada al backend, utilizar **mock data realista y visualmente coherente**.

La aplicación debe ser:

* Android nativo.
* Java.
* XML.
* Android Studio.
* API 34 / Android 14 como mínimo.

NO utilizar:

* Kotlin.
* Jetpack Compose.
* Flutter.
* React Native.
* Interfaces híbridas.

La interfaz debe construirse mediante XML y componentes Android/Material apropiados.

Se permite utilizar:

* Activities.
* Fragments.
* RecyclerView.
* Navigation Component.
* ViewModel.
* LiveData.
* Material Components.
* Drawables.
* ShapeDrawables.
* Custom Views cuando aporten valor visual o de reutilización.

La implementación debe favorecer la separación entre:

**UI → estado de UI → datos/mock data**

sin introducir complejidad innecesaria.

# 5. PRINCIPIOS DE DISEÑO

Todos los diseños deben seguir estos principios.

## 5.1. Jerarquía

Cada pantalla debe tener claramente:

1. Elemento principal.
2. Información secundaria.
3. Acciones principales.
4. Información complementaria.

El usuario debe entender rápidamente:

> ¿Dónde estoy?
> ¿Qué estoy viendo?
> ¿Qué puedo hacer aquí?
> ¿Cuál es la acción principal?

---

## 5.2. Progressive disclosure

No mostrar toda la información simultáneamente.

Primero:

**información esencial**

y después:

**información secundaria bajo demanda.**

Utilizar:

* Expandibles.
* Bottom sheets.
* Dialogs.
* Secciones.
* Tabs.
* Detalles desplegables.

cuando sea apropiado.

---

## 5.3. Consistencia

Los mismos conceptos deben verse iguales en toda la aplicación.

Por ejemplo:

* Hotel card → siempre misma estructura base.
* Rating → mismo componente.
* Chip → mismo sistema.
* Precio → misma jerarquía.
* Botón primario → mismo lenguaje visual.
* Estados → mismo código visual.
* Headers → estructura coherente.

# 11. FOTOGRAFÍA

* Thumbnails.
* Image overlays.

En una aplicación hotelera:

> **la fotografía es información.**

Debe ayudar al usuario a decidir.

* Métricas.

No obstante, debe seguir perteneciendo al mismo Design System.

---

# 48. NAVEGACIÓN

Diseñar una navegación coherente.

Para el cliente considerar:

**Inicio | Buscar | Reservas | Taxi | Perfil**

No necesariamente utilizar exactamente esta estructura si una alternativa produce una mejor UX.

La navegación debe decidirse según:

* Frecuencia.
* Importancia.
* Contexto.
* Jerarquía.

No agregar una sección al Bottom Navigation solamente porque existe una funcionalidad.

---

# 49. BOTTOM NAVIGATION

Debe contener únicamente destinos principales.

Evitar:

* Más de 5 destinos.
* Iconos ambiguos.
* Labels inconsistentes.
* Navegación redundante.

El estado activo debe ser extremadamente claro.

---

# 50. ESTADOS DE UI

Cada pantalla importante debe diseñarse considerando:

## Loading

Skeletons cuando sea apropiado.

## Empty

Ejemplo:

> No tienes reservas todavía.

Incluir ilustración/icono y CTA.

## Error

Mensaje comprensible + acción para reintentar.

## Success

Confirmación clara.

## Disabled

Estados visuales coherentes.

## Offline/API unavailable

Informar sin romper toda la experiencia.

---

# 51. SKELETON LOADING

Para contenido visual como:

* Hotel cards.
* Room cards.
* Booking cards.

preferir skeleton loading en lugar de una pantalla completamente bloqueada.

Debe conservar la estructura de la interfaz mientras carga.

---

# 52. EMPTY STATES

Crear empty states reutilizables.

Ejemplo:

```text
        [ illustration ]

     Aún no tienes reservas

   Explora hoteles y encuentra
       tu próxima estancia.

      [ Buscar hoteles ]
```

Debe existir una identidad visual consistente.

---

# 53. ERROR STATES

Evitar mensajes técnicos como:

> NullPointerException

o

> HTTP 500.

Mostrar mensajes orientados al usuario.

Ejemplo:

> No pudimos cargar los hoteles.

> Intenta nuevamente en unos segundos.

[ Reintentar ]

---

# 54. DIALOGS Y BOTTOM SHEETS

No utilizar Dialogs indiscriminadamente.

Usarlos cuando:

* Se necesita una decisión.
* La información es contextual.
* No merece una pantalla completa.

Usar Bottom Sheets para:

* Filtros.
* Ordenamiento.
* Selección rápida.
* Información contextual.

---

# 55. MICROINTERACCIONES

La interfaz debe sentirse viva.

Cuando sea técnicamente razonable, incorporar:

* Ripple.
* Press states.
* Transiciones suaves.
* Cambios de estado.
* Animaciones cortas.
* Feedback visual.
* Expansión de cards.
* Selección de chips.

No utilizar animaciones únicamente por decoración.

La regla es:

> **animar para comunicar, no para presumir.**

---

# 56. ACCESIBILIDAD

Diseñar teniendo en cuenta:

* Contraste.
* Tamaños táctiles adecuados.
* Texto legible.
* Labels.
* Iconos comprensibles.
* No depender únicamente del color.
* Estados claramente diferenciables.

Los botones importantes deben ser fáciles de pulsar.

---

# 57. RESPONSIVIDAD

Aunque el objetivo principal sea Android móvil, las vistas deben soportar diferentes tamaños de pantalla razonablemente.

Evitar:

* Coordenadas absolutas.
* Elementos que se corten.
* Textos que desborden.
* Imágenes deformadas.

Utilizar correctamente:

* ConstraintLayout.
* LinearLayout.
* FrameLayout.
* ScrollView.
* RecyclerView.

según corresponda.

---

Crear una biblioteca interna de componentes.

Como mínimo:

### Navigation

* AppHeader.
* BottomNavigation.

### Hotels

* HotelCard.
* HotelImageGallery.
* RatingBadge.
* HotelInfoSection.

### Rooms

* RoomCard.
* RoomFeature.

### Services

* ServiceChip.
* ServiceCard.
* ServiceSection.

### Booking

* BookingCard.
* BookingSummary.
* BookingStatus.
* PriceBreakdown.

### Taxi

* TaxiRequestCard.
* DriverCard.
* VehicleCard.
* TaxiStatus.
* QRView.

### UI

* PrimaryButton.
* SecondaryButton.
* IconButton.
* SearchField.
* DateSelector.
* GuestSelector.
* FilterChip.
* EmptyState.
* ErrorState.
* LoadingSkeleton.

---

# 59. COMPONENTES COMO SISTEMA

Los componentes no deben ser simplemente XMLs copiados y pegados.

Cada componente debe:

* Tener una responsabilidad clara.
* Poder reutilizarse.
* Permitir estados.
* Mantener el mismo estilo.
* Evitar duplicación.

Por ejemplo:

**HotelCard**

debe poder utilizarse en:

* Home.
* Search.
* Recommendations.
* Favorites si se implementan.

---

# 60. MOCK DATA

Mientras no exista backend:

utilizar mock data.

Los datos deben parecer reales.

NO utilizar repetidamente:

```text
Hotel 1
Hotel 2
Hotel 3
```

Utilizar datos plausibles:

* Nombres de hoteles.
* Fotografías.
* Precios.
* Ratings.
* Ubicaciones.
* Servicios.
* Habitaciones.
* Reservas.

Esto es importante porque una interfaz de alta calidad pierde credibilidad cuando los datos parecen artificiales.

---

# 61. CONTENIDO VISUAL

El diseño debe contemplar:

* Textos suficientemente realistas.
* Longitudes variables.
* Hoteles con nombres cortos y largos.
* Precios distintos.
* Diferentes cantidades de servicios.
* Ratings diferentes.
* Estados distintos.

Esto permitirá comprobar que los componentes realmente son robustos.

---

# 62. NO DISEÑAR SOLO EL "HAPPY PATH"

Cada pantalla importante debe considerar:

* Estado normal.
* Loading.
* Empty.
* Error.
* Success.
* Disabled.
* Long content.
* Sin fotografía.
* Muchos servicios.
* Sin servicios.
* Precio elevado.
* Precio bajo.
* Rating alto.
* Rating bajo.

El objetivo es que la interfaz siga siendo coherente en todos estos casos.

---

# 63. DISEÑO DE LA EXPERIENCIA COMPLETA

El usuario debe sentir una progresión natural:

```text
DESCUBRIR
   ↓
BUSCAR
   ↓
EXPLORAR
   ↓
COMPARAR
   ↓
ELEGIR
   ↓
RESERVAR
   ↓
PAGAR
   ↓
DISFRUTAR
   ↓
CHECKOUT
   ↓
CALIFICAR
   ↓
TRANSPORTE
```

Cada etapa debe tener una interfaz diseñada específicamente para su objetivo.

No reutilizar indiscriminadamente la misma estructura.

---

# 64. JERARQUÍA VISUAL DEL PRODUCTO

La aplicación debe priorizar visualmente:

### Nivel 1

* Hotel.
* Fotografía.
* Destino.
* Precio.
* Disponibilidad.

### Nivel 2

* Rating.
* Servicios.
* Habitación.
* Fechas.

### Nivel 3

* Información secundaria.
* Detalles administrativos.
* Metadatos.

La información secundaria nunca debe competir visualmente con la acción principal.

---

# 65. BOTONES Y CTA

Definir una jerarquía clara:

### Primary

Acciones fundamentales:

* Buscar.
* Reservar.
* Confirmar.
* Pagar.
* Seleccionar.

### Secondary

Acciones importantes pero no principales.

### Tertiary

Acciones secundarias.

### Destructive

* Cancelar.
* Eliminar.
* Rechazar.

No utilizar el mismo estilo visual para todas las acciones.

---

# 66. PRECIOS

El precio es información crítica en una aplicación hotelera.

Debe tener una jerarquía fuerte.

Ejemplo:

```text
Desde

S/ 280
por noche
```

o:

```text
S/ 1,120
4 noches
```

No hacer que el precio compita con el nombre del hotel, pero tampoco esconderlo.

---

# 67. ESTADOS Y BADGES

* Confirmada.
* Activa.

* En camino.
* Finalizada.
* Incluido.
* Adicional.

* Tipografía.
* Padding.
* Radius.
* Iconografía.
* Jerarquía.

---

# 68. MAPAS

Cuando sea necesario representar ubicación:

utilizar una interfaz de mapa integrada visualmente con el producto.

El mapa no debe dominar toda la aplicación.

Debe servir para:

* Ubicación del hotel.
* Lugares cercanos.
* Seguimiento del taxi.

# 69. QR

El QR debe tener suficiente espacio alrededor.

No colocarlo como un elemento pequeño dentro de una card.

Cuando el usuario necesita escanearlo:

> convertirlo en el elemento principal de la pantalla.

# 70. PERFIL Y CONFIGURACIÓN

# 71. CONSISTENCIA ENTRE ROLES

Aunque cliente, administrador, conductor y Superadmin tengan interfaces diferentes:

* Tipografía.

# 72. DIFERENCIACIÓN ENTRE ROLES

La diferencia debe producirse principalmente mediante:

**información + navegación + densidad + acciones**

Administrador:

# 82. REGLA FUNDAMENTAL SOBRE BACKEND

Este prompt NO debe interpretarse como una solicitud para diseñar o implementar el backend.

No dedicar esfuerzo innecesario a:

* Base de datos.
* APIs.
* Endpoints.
* Arquitectura de servidores.
* Persistencia.
* Autenticación real.
* Seguridad backend.
* Lógica distribuida.

Cuando una funcionalidad necesite datos:

> utilizar interfaces y mock data bien estructurados.

La implementación debe quedar preparada para conectar posteriormente la fuente de datos real.

---

# 83. REGLA FUNDAMENTAL SOBRE UI

No diseñar únicamente pensando:

> “¿Qué componentes necesito para cumplir el requisito?”

Diseñar pensando:

> “¿Cuál es la mejor experiencia posible para que un usuario real complete esta tarea?”

El requisito funcional define **qué existe**.

El diseño define **cómo se experimenta**.

---

# 84. REGLA FUNDAMENTAL SOBRE REUTILIZACIÓN

Evitar dos extremos:

### Extremo 1

Copiar y pegar cada XML.

### Extremo 2

Crear un sistema de abstracciones tan complejo que dificulte modificar la UI.

Buscar un punto intermedio:

> **componentes reutilizables, simples y visualmente consistentes.**

El resultado final debe ser una aplicación móvil que visualmente pueda describirse como:

> **una plataforma moderna de hospitality con la riqueza visual de una aplicación de viajes y la disciplina de diseño de una herramienta profesional.**

Debe ser:

* Moderna.
* Elegante.
* Visual.
* Clara.
* Rápida de comprender.
* Consistente.
* Reutilizable.
* Accesible.
* Escalable.
* Profesional.

La aplicación debe tener una identidad propia.

No debe parecer:

* Booking.
* Airbnb.
* Uber.
* Un dashboard administrativo.
* Una plantilla Material.
* Un proyecto universitario genérico.

Debe parecer un producto nuevo que podría convertirse en una aplicación comercial real.

# 86. PRINCIPIO FINAL

La prioridad del proyecto frontend es:

**EXPERIENCIA > ESTÉTICA AISLADA**

y

**CONSISTENCIA > DECORACIÓN**

y

**CLARIDAD > CANTIDAD DE ELEMENTOS**

y

**CALIDAD DE LAS PANTALLAS PRINCIPALES > CANTIDAD DE PANTALLAS**

y

**REUTILIZACIÓN > COPIAR Y PEGAR**

y, especialmente:

> **El usuario debe poder reservar un hotel sin pensar demasiado en cómo utilizar la aplicación.**

La interfaz debe hacer que la complejidad del sistema desaparezca detrás de una experiencia sencilla, visual y natural.

El objetivo no es simplemente que la aplicación "se vea bonita".

El objetivo es que **se sienta diseñada**.
